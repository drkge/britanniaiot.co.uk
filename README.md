# britanniaiot.co.uk

The Britannia IoT Solutions website. A Jekyll site built natively by GitHub Pages — push
to `main` and it deploys. Live at <https://britanniaiot.co.uk>.

## Layout

```
_config.yml                site-wide settings: company details, contact, URLs
_layouts/default.html      the page shell — <head>, meta, structured data wrapper
_includes/header.html      nav (shared by every page)
_includes/footer.html      footer, contact details, statutory company line
_includes/nav-js.html      mobile menu toggle
_includes/schema-common.json   Organization + WebSite structured data

index.html   404.html   about/   contact/   faq/   how-it-works/   privacy/
solutions/   + fill-level-sensors/  route-optimisation/  analytics-reporting/
sectors/     + local-authorities/   waste-contractors/
               universities-nhs-estates/  tourism-coastal-parks/
results/     + stralsund-smart-street-bins/  vejle-dynamic-round-planning/
               fano-seasonal-recycling-sites/  langeland-island-recycling-network/
resources/   + waste-sensor-glossary/  sensor-led-vs-fixed-frequency-collections/

assets/css/style.css       the only stylesheet
assets/img/                logo, icons, Open Graph card
robots.txt  llms.txt       static, copied through unchanged
```

Each page is `<dir>/index.html` with YAML front matter and the page body only. The
`<head>`, nav and footer come from the layout — change them **once**, in `_includes/`.

## Editing

**Site-wide things** — company number, registered office, email, phone, domain — live in
`_config.yml` and render into the footer and structured data.

**Per-page front matter:**

```yaml
---
layout: default
title: "≤60 chars, unique"          # <title>, og:title, twitter:title
description: "130–158 chars"        # meta description + OG/Twitter
keywords: "optional"
nav: solutions                      # highlights the nav item; omit if none
schema_json: |                      # page-specific structured data
  { ... }
---
```

`schema_json` holds only this page's nodes — `WebPage`, `BreadcrumbList`, and any
`FAQPage` / `Service` / `Article` / `HowTo` / `DefinedTermSet`. The shared `Organization`
and `WebSite` nodes come from `_includes/schema-common.json`, and the layout assembles
them into one `@graph`. Keep the JSON valid; a broken block is worse than none.

Canonical URLs, OG tags and the robots meta are all derived automatically — don't
hand-write them.

**Adding a page:** create `new-page/index.html` with the front matter above. `sitemap.xml`
is generated by `jekyll-sitemap`, so it updates itself. Add the page to `llms.txt` by hand
if it should be visible to answer engines.

## Local preview

```bash
bundle install     # one time
./serve            # http://localhost:4173
```

**This needs Ruby 2.7 or newer.** macOS ships Ruby 2.6, on which the `github-pages` gem
will not install — `ffi` requires Ruby ≥ 3.0. To set it up:

```bash
brew install ruby
echo 'export PATH="/opt/homebrew/opt/ruby/bin:$PATH"' >> ~/.zshrc
```

Without it, push and let GitHub Pages build. A failed build leaves the previously
published version serving, and GitHub emails you the error, so a broken build cannot take
the live site down.

## GitHub Pages

Settings → Pages → deploy from `main`, root folder. Already configured.

- `CNAME` holds the custom domain. **Don't delete it** — Pages reads it on every build.
- **No `.nojekyll`** — that file would disable Jekyll entirely and this site needs it.
- `404.html` uses `permalink: /404.html` so Pages picks it up for missing paths.
- `jekyll-sitemap` is a natively supported plugin; no CI or Actions workflow is required.
- The site **must** be served from a domain root. Internal links are root-relative, so a
  project-page subpath (`drkge.github.io/britanniaiot.co.uk/`) breaks all of them. The
  custom domain is what makes it work.

DNS at LCN: four A records to `185.199.108-111.153`, four AAAA to
`2606:50c0:8000-8003::153`, and `www` CNAME to `drkge.github.io`.

There is no `_headers` file — that was a Netlify/Cloudflare feature and does nothing on
GitHub Pages, so security headers and asset cache-control aren't available. Put Cloudflare
in front of the domain if you want them.

## Search engines

Both consoles are verified and the sitemap is submitted. Files at the site root
that look like cruft but are not — **do not delete these**:

- `BingSiteAuth.xml` — Bing Webmaster Tools ownership token. Also published as an
  `msvalidate.01` meta tag from `bing_site_verification` in `_config.yml`; both carry
  the same token, so either satisfies Bing.
- `f3e602c1a930089c306876cbc32a314c.txt` — the IndexNow key. Its filename *is* the key, and it must
  match `indexnow_key` in `_config.yml`. IndexNow proves ownership by fetching it.

Google Search Console is a **Domain property**, verified by a DNS TXT record at LCN,
not by anything in this repo. There are two `google-site-verification` TXT records on
the domain: one is Search Console, the other verifies Google Workspace for email.
Removing the wrong one breaks mail — leave both alone.

After publishing new or changed pages:

```bash
python3 _tools/indexnow.py
```

That pushes every sitemap URL to Bing, Yandex, Naver, Seznam and Yep in one call.
Only run it when pages have actually changed; repeatedly submitting unchanged URLs
counts against you. Google has no equivalent — it retired its ping endpoint in 2023
and only accepts sitemaps through Search Console.

`sitemap.xml` is generated by `jekyll-sitemap`, so it stays current by itself. If you
add a page, update `llms.txt` by hand — nothing generates that.
